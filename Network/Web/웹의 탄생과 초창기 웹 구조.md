

# 웹의 탄생
웹은 1989년 유럽 입자 물리학 연구소(CERN)에서 연구하던 **Tim Berners-Lee**에 의해 개발되었다.

그는 논문 관련 정보를 레퍼런스 하기가 너무 힘들었다. 특정 논문을 참조에 적어 둘 때, 오늘날과 다르게 하나하나씩 논문을 직접 찾아야 했기 때문이다.

이에 버너스 리는 텍스트에 링크가 있어서 참조 논문의 페이지로 이동할 수 있다면 훨씬 수월하게 논문을 찾을 수 있을 것이라 생각하여 텍스트에 링크(하이퍼텍스트)를 추가해 확장하고자 하였고, 이렇게 만들어진 문서 형식이 **HTML(Hyper Text Markup Language)** 이다.

이 HTML 문서를 송수신하기 위해 **HTTP 프로토콜**을 만들고 웹 페이지를 표시하고 링크를 통해 문서를 탐색할 수 있는 최초의 **웹 브라우저**이자 편집기인 **World Wide Web (WWW)**와 **통합 자원 식별자, Uniform Resource Locator(URL)** 등을 개발하였다.

# 초창기 웹 구조
초창기 웹은 **단방향 구조**로, 클라이언트에서 서버에게 요청을 하면 서버가 요청한 정보를 제공하는 단순한 형태였다.

웹은 기본적으로 **웹 클라이언트**와 **웹 서버**로 구성되며, 이것은 클라이언트-서버 구조로 볼 수 있다.

웹 클라이언트는 우리가 **브라우저**라고 부르는 프로그램이며 **인터넷(Public Network)**를 통해 웹 서버와 연결된다.

1. 클라이언트가 브라우저에 url 입력
2. 브라우저가 DNS 서버에 요청을 보내 해당 url의 ip 주소를 받아온다.
3. 알아낸 ip주소로 브라우저가 요청(http request)를 보낸다.
4. 서버가 요청(http request)를 받고 HDD에서 요청에 해당하는 문서를 찾는다.
5. 문서를 찾은 뒤 다시 클라이언트에게 보낸다(http response)
6. 클라이언트는 받은 html 문서를 랜더링 한다.

# 초창기 브라우저
상호작용이 단순함에 따라 브라우저의 역할은 크지 않았고, 문서 뷰어와 비슷한 수준이었다.

당시 브라우저의 역할은 다음과 같다.

1. 구문분석(Parser) :
	전송받은 HTML 파일은 단순한 텍스트와 달리 `<tag>`라는 구조를 가진 태그가 포함되어있다. 브라우저 내의 분석기(Parser)**가 이 텍스트를 읽고 분법적으로 분석하여 컴퓨터가 이해할 수 있는 자료구조로 변환하는 과정으로 DOM(Document Object Model)이라는 비선형 트리 구조로 형성된다. 
2. 랜더링 : 
	파싱을 통해 만들어진 DOM 구조를 바탕으로, 실제 사용자 화면에 시각적인 요소(텍스트, 이미지 등)을 출력하는 과정으로 초창기의 브라우저는 이 두 가지의 핵심 기능만 수행하면서 '문서를 가져와서 보여주는' 문서 뷰어의 역할을 충실히 수행하였다.

# 초창기 웹의 문제점
http 프로토콜은 클라이언트와 서버가 이미 TCP/IP로 연결되어 있음을 전제로 하고 있기 때문에 연결의 상태를 저장하지 않았다. (Statelessness, 무상태성)

> [!CAUTION] 주의
> 이 TCP 연결은 HTTP 통신 과정 동안 유지되지는 않는다.

![statelessness](../../img/Pasted%20image%2020260905180510.png)
> *Statelessness*


http의 무상태성은 서버 부하를 감소시키고 높은 확장성(Scalability)를 가졌고 어떤 요청이든 여러 서버 중 유후 서버에 분산 처리가 가능했다. 

하지만 상태 유지가 없기 때문에 현재 우리가 당연하게 사용하는 기능(로그인, 장바구니 등)들이 불가능했고 매 요청마다 연결이 새로 설정되어야 했다.

현대에는 이 무상태성 문제를 해결하기 위한 기술로 쿠키, 세션등이 도입되었다.

> [!NOTE]- TCP/IP와 HTTP의 차이
> HTTP는 하위 계층인 TCP/IP 위에서 작동한다. TCP/IP는 **연결 지향(Connection-Oriented)** 프로토콜이기 때문에 **'연결'** 이라는 상태(State) 개념을 포함한다. 
> 
> | 통신 프로토콜 | 특징                         | 상태(State) 여부 | 비유                 |
| ------- | -------------------------- | ------------ | ------------------ |
| TCP     | 연결 지향(Connection-Oriented) | O (상태를 기억)   | 전화 통화 (연결 유지)      |
| HTTP    | 비연결성(Stateless)            | X (상태를 잊음)   | 단문 문자 (요청/응답 후 종료) |

# 웹의 3가지 핵심 요소
웹이 복잡해지고, 요구 사항이 늘어남에 유지보수의 편의성을 위해 3가지로 분리하였는데 아래와 같다.

1. 자료구조(data) : HTML 문서 자체가 이 자료 구조에 해당한다.
2. 인터페이스(ui) : 문서를 보거나 사람의 제어가 가능한 인터페이스가 필요하다.
3. 제어 체계(logic) : 이 모든 것에 대한 제어 체계가 필요하다.

기능들을 모듈로 잘라 쪼갤 때, 이 세 가지 요소는 반드시 각자의 모듈로 분리해야하는 최소화의 규칙으로 작용한다.


# 발전하는 웹

## 클라이언트의 발전
### CSS의 등장(UI)
초기 웹에서, 자료구조인 html은 단순히 데이터를 표현하였다.

하지만 시간이 지나면서 html의 시각적 표현을 개선할 필요성이 증가하였고 html 내부에 스타일링 기능을 추가하였으나, 유지보수가 어려워지며 분리한 것이 CSS이다.

CSS는 웹 페이지의 시각적 표현을 담당하며, 브라우저에게 랜더링을 지시하는 문서이다.

### JS의 등장(Logic)
웹이 복잡해지면서 서버로부터 클라이언트가 단방향으로 정보를 받아오던 과거와 달리, 양방향 통신(상호작용)의 필요성이 커졌다.

양방향 소통을 위해서는 웹 페이지가 동적으로 작동해야했고 이에 자바스크립트(JS)가 등장하게 되었다.

자바스크립트는 클라이언트에서 **제어(Logic)**의 역할을 수행하며, 브라우저는 스크립트 엔진이 추가되어 자바스크립트를 지원하게 되었다.

### 쿠키의 등장(상태 저장)
양방향 통신을 하게 되며 통신 과정 중, 상태(State)를 저장할 필요가 생겼다.

하지만 http는 stateless 프로토콜이기 때문에 이 **상태를 따로 기록하기 위해 쿠키가 도입**되었다. (서버는 DB 사용)


## 서버의 발전
### DB의 등장(Model)
양방향 통신을 도입함에 따라 각종 상태를 기록하기 위해서 서버에 데이터베이스(DB)가 추가되었다.

데이터베이스는 서버 측 상태와 데이터를 저장하고 조회하는 역할을 하며, WAS(Web Application Server)와 SQL을 통해 소통한다.

### 웹 서버의 역할 분화(View)
기존 웹 서버는 클라이언트와의 단순 통신 및 파일 전달이 주된 역할이었으나 시스템이 분화하면서 사용자의 요청을 받고 화면을 구성하는 파일이나 데이터를 건네주는 View(인터페이스) 역할로 전문화되었다.

### WAS의 등장(Controller)
서버의 로직이 복잡해짐에 따라 이를 처리하는 처리 주체를 따로 분리하였고 그것이 바로 **WAS(Web Application Server)** 이다.

> [!NOTE] 시스템 연동 흐름
> **클라이언트 -> 웹 서버(View) -> WAS(Controller) -> 데이터베이스(Model)**
> 
> 클라이언트가 요청한 작업이 정적 파일(HTML 등)의 요청인 경우 웹 서버에서 처리하고, 복잡한 연산이 필요한 요청인 경우 WAS로 보내 데이터베이스의 조회 등의 작업을 수행한다.

# 현대의 웹 서버
웹 서버는 초창기의 클라이언트의 요청에 HTML 파일을 응답으로 제공하는 단순 정보 제공을 넘어서, **WAS와의 협업을 통해 사용자의 데이터를 가공하고 연산하는 동적인 웹 서비스 구조로 발전하였다.**

> [!NOTE] 웹 서버의 의미
> 1. **하드웨어 측면에서의 웹 서버** : 웹 서버는 웹 서버 소프트웨어와 웹사이트의 구성 파일들(예: HTML 문서, 이미지, CSS 스타일시트, JavaScript 파일)을 저장하는 컴퓨터이다. 인터넷에 연결되어 있으며, 웹에 연결된 다른 기기들과의 물리적인 데이터 교환을 지원.
> 
> 
>2. **소프트웨어 측면에서의 웹 서버** : 웹 서버는 웹 사용자가 호스팅된(서버에 저장된) 파일들에 접근하는 방식을 제어하는 여러 구성 요소를 포함하며, 최소한의 기본 단위로 보면 이는 'HTTP 서버'를 의미한다. HTTP 서버는 URL(웹 주소)과 HTTP(브라우저가 웹페이지를 보기 위해 사용하는 통신 규약)를 이해하는 소프트웨어로 자신이 저장하고 있는 웹사이트의 도메인 이름을 통해 접근할 수 있으며, 이 웹사이트들의 콘텐츠를 최종 사용자의 기기로 전달해 준다.

여기서 **정적 웹 서버**는 HTTP 서버(소프트웨어)가 있는 컴퓨터(하드웨어)로 구성되며 서버가 호스팅된 파일을 브라우저로 보내기 떄문에 '정적'이라 한다.

**동적 웹 서버**는 정적 웹 서버와 추가 소프트웨어, 가장 일반적으론 애플리케이션 서버와 데이터베이스이다. 여기서 애플리케이션 서버가 HTTP 서버를 통해 브라우저로 콘텐츠를 보내기 전에 호스팅된 파일을 업데이트하기 때문에 '동적'이라고 부른다.

예를 들어 브라우저에서 볼 수 있는 최종 웹페이지를 생성하려면 애플리케이션 서버가 데이터베이스의 콘텐츠로 HTML 템플릿을 채운다. 일반적으로 이러한 종류의 사이트는 수천 개의 정적 HTML 문서가 아닌 몇 개의 HTML 템플릿과 데이터베이스로 구성되어 있다.

# CGI
>Common Gateway Interface


공용 게이트웨이 인터페이스(CGI)는 웹 서버가 사용자의 요청을 받아 외부 애플리케이션(프로그램)을 실행하고, 그 결과를 다시 웹 브라우저로 전송할 수 있도록 연결해주는 표준 규약

초기 웹은 단순히 미리 만들어진 HTML 문서(정적페이지)만 보여줄 수 있었으나 사용자의 입력에 따라 데이터를 처리하고 결과를 보여주는 '동적 웹 페이지(로그인, 게시판, 검색결과)' 를 만들기 위해 CGI를 도입하였다.


 **작동 방식**
1. 사용자가 웹 브라우저를 통해 서버에 정보 요청
2. 웹 서버가 요청을 확인하고, 처리에 필요한 특정 CGI 스크립트나 프로그램을 호출하여 독립된 프로세스를 생성(fork)
3. CGI 프로그램이 데이터베이스와 통신하거나 필요한 연산을 수행한 후 결과물(주로 HTML)을 만들어냄
4. 결과물을 웹 서버를 거쳐 사용자의 웹 브라우저로 전달
5. 응답이 끝나면 해당 CGI 프로세스 즉시 종료

장점 : C, C++, Python, Perl 등 다양한 프로그래밍 언어로 작성할 수 있어 언어 독립적이고 구조가 단순하여 구현이 쉽다.

단점 : 요청이 들어올 때마다 매번 새로운 프로세스를 생성하고 종료해야하기 때문에 사용자 요청이 많을 경우 서버의 메모리와 CPU에 과부화가 발생하여 성능이 크게 떨어짐

위 단점을 해결하기 위해서 현대에는 한 번 생성된 프로세스를 재사용하는 **FastCGI**나 웹 서버 안에 스크립트 실행 엔진을 내장하는 방식 (PHP의 mod_php 등), 별도의 웹 애플리케이션 서버(WAS)를 두는 방식 등이 등장


- API 와의 차이 : CGI는 웹 서버와 외부 프로그램간의 실행/연결 규약임
